## 5. 根因与主要修改

### 5.1 根因

1. 输入只要求“相关经历”，没有明确要求粘贴要改的具体一句/一段，也没有展示可选核对问题。
2. provider JSON 合同只有宽泛的 JD 分析字段，缺少编辑对象、候选文本、证据核对和完成标准。
3. 质量门主要检查结构与来源，没有拦住“语法合法但普通学生看不懂、无法开始”的行动。
4. 编排器把“可独立完成……”一类能力宣称当成直接经历支撑，诱导生成并不一定真实的修改动作。
5. UI 用抽象短评当主标题，并把相似判断分散到多个结果卡；记录页也没有把核对对象和有条件候选文本带入闭环。

### 5.2 修改

- 新增 `src/domain/jd-action-clarity.ts`：区分直接动作、能力宣称和无证据输入。
- JD 合同新增 `revisionTarget`、`candidateRevision`、`evidenceCheck`；所有非失败行动补 `completionStandard`。
- Prompt 明确：能力宣称不得当作已发生动作；证据不足时候选文本必须为 `null`；同一句原文不能散落重复。
- mock 与 orchestrator 对能力宣称统一降级为证据核对行动，不再补写简历。
- provenance 与 API 二次校验修复轻复盘事实来源，同时保持未知事实拒绝规则。
- 行动质量门加入 JD 可理解性/可执行性负例：必须有核对对象、证据动作、完成标准；无支撑不得给候选句。
- JD 输入页要求逐字粘贴要核对的一句或一小段，并提示可查项目文档、截图、版本记录或交付物。
- 行动页固定为“今天只做这一件事”，明确预计时间、完成后记录、完成标准；证据不足结果合并为一个“证据与候选文本”块。
- 记录页预填 `revisionTarget`；只有证据充分时才预填候选文本。
- 增加单元和生产 E2E，覆盖截图同类能力宣称、同句重复上限、候选句边界、记录预填和移动端。
