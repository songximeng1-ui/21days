# “21天”MVP发展总方向

**版本：V1.0**
**日期：2026年7月23日**

> 前期证明“有用”，中期证明“可重复”，后期证明“可规模化并形成复利型壁垒”。

## 0. 文档定位与最高优先级

本文用于统一“21天”MVP从当前验证阶段到中长期发展的产品总方向。它不是单个版本的功能清单，也不替代具体PRD、技术方案和分支执行文档。

本文档位于《21天总准则》之下，作为当前MVP之后的阶段路线、数据飞轮、模型策略、商业边界和长期壁垒说明。执行层级为：

1. 《21天总准则》：最高产品准则。
2. 《21天MVP发展总方向_V1.0》：中长期发展方向与阶段升级原则。
3. 《新MVP PRD》及各专项MVP准则：当前版本的具体产品、体验、数据、安全、测试与研发执行依据。
4. 《项目协作准则》：跨agent和跨任务协作方式。

如本文与《21天总准则》、已确认的专项准则或后续明确决策发生冲突，以《21天总准则》和最新明确决策为准。

本文第10节的P0/P1/P2是路线图优先级，不自动扩大当前版本的研发范围。当前版本实际实现边界仍以《新MVP PRD》《MVP PM决策共识》《MVP 研发边界决策》和正在执行的分支任务说明为准。

参考外部成熟求职工具、Agent workflow、Skill 仓库或自动化系统时，必须服从《21天总准则》中的“当前 MVP 外部成熟方案吸收准则”：当前阶段只吸收能强化真实材料、今日行动、真实记录、轻复盘和下一轮调整闭环的原则与轻量机制，不因外部方案完整或自动化程度高而扩大当前 MVP 主线范围。

### 不变的产品原则

1. 真实有效优先：面对真实岗位、真实能力差距和真实反馈。
2. 行动优先：AI输出以用户是否执行和是否产生状态变化衡量。
3. 具体可执行优先：任务必须明确对象、动作、完成标准和下一步。
4. 用户现实优先：考虑学历、专业、城市、时间、经济压力和心理阻力。
5. 情绪承接服务于行动：使用低压力和行为科学设计，但不恐吓、夸大或操控。
6. 简洁与高价值反馈：每个问题和入口都必须影响状态、计划或结果。
7. 四路线共享底座：独立呈现和验证，共享状态、任务、反馈和结果结构。
8. 真实岗位约束：岗位搜索、验证和匹配必须基于可核验的真实岗位；在当前 MVP 阶段不得表现为自动抓岗、批量岗位排序、匹配分或录取概率。

**产品定义：**面向普通本科应届生，以用户状态识别、真实行动任务、持续反馈调整和结果验证为核心的AI求职行动系统。21天是产品外壳，状态变化和真实进展才是交付物。

## 1. 长期不变的产品骨架

用户初始状态 → 路线与问题判断 → 今日行动任务 → 用户执行 → 反馈与证据 → 状态更新 → 计划调整 → 求职结果

产品由五层组成：体验层、状态层、决策层、模型层、数据与评估层。

**产品大脑 = 用户数据库 + 状态判断 + 干预策略 + 评估系统 + 模型能力。**

## 2. 阶段划分

| 维度 | 前期 | 中期 | 后期 |
|---|---|---|---|
| 核心问题 | 是否真的有用 | 效果能否稳定复制 | 能否规模化并形成复利壁垒 |
| 产品 | 跑通闭环 | 用户分层、动态计划、验证过的干预路径 | 完整职业行动系统，21天作为入口 |
| 数据 | 完整记录发生了什么 | 判断对谁、何时、做什么更有效 | 行为—干预—结果数据库与数据飞轮 |
| 模型 | 云端优先 | 规则＋多模型路由 | 云端＋私有混合部署 |
| 商业 | 验证付费意愿 | 验证单位经济和稳定渠道 | B2C规模化，谨慎扩展B2B/API |

## 3. 前期：证明有用

### 阶段目标

证明普通本科应届生使用产品后，比独自摸索更快完成关键行动并改善求职状态。

### 产品形态

- 四状态分流，共享统一底座。
- 21天计划有阶段骨架，但根据反馈动态调整。
- 每日任务包含目的、原因、动作、标准、耗时、证据和下一步。
- 反馈不仅记录完成，还记录质量、阻力和未完成原因。
- 结果记录方向、材料、岗位、投递、回复、面试等状态变化。

### 最小数据库

UserProfile、JourneyState、Plan、Task、TaskExecution、Feedback、Intervention、ArtifactVersion、JobApplication、Outcome、ModelTrace。

### 北极星指标

**21天有效进展率：**进入计划的目标用户中，在21天内完成关键行动，并产生至少一项可验证求职状态改善的比例。

前期重点指标：激活、任务执行、证据提交、3/7/14/21天有效留存、状态进展、求职结果、AI采纳与错误率、单用户成本和人工介入时间。

### 进入中期的证据

- 约30—50名真实目标用户测试，包含陌生用户。
- 约10—20名较完整走过核心流程。
- 出现多例可验证进展。
- 能解释流失点、无效任务和有效任务。
- 有用户愿意付费、推荐或继续使用。
- 核心流程不依赖创始人逐个救火。

### 前期不做

不训练基础大模型，不建设正式GPU服务，不做复杂社区、全职业覆盖和大量边缘功能，不用注册数、对话数和生成字数证明价值。

## 4. 中期：证明可重复

### 产品形态

- 建立可操作的用户分层。
- 根据执行和反馈持续更新状态、重排任务。
- 建立任务策略库、阶段评估和实验系统。
- AI自动完成大部分流程，人工只介入高价值节点。

### 数据库升级

建立用户、任务、干预、材料版本、结果和实验标签体系，回答：哪类用户在什么状态下，执行什么任务、接受什么干预，更可能获得什么结果。

### 模型策略

规则和低价模型负责结构化、高频任务；中等模型负责个性化任务表达；高质量模型负责复杂职业判断、路线调整和关键反馈；建立任务级评测、路由、备用和降级。

### 指标

结果稳定性、分层效果、付费转化、推荐、退款、获客成本、单用户模型和人工成本、毛利、人工介入时长、任务级模型质量。

### 进入后期的证据

陌生用户稳定进入；不同批次结果相对稳定；增长不同比增加人工；单位经济可持续；数据库开始反向改善分层、任务和计划；关键流程具备监控、版本和降级。

## 5. 后期：规模化与壁垒

### 产品形态

21天继续作为求职启动入口，底层逐步扩展到方向判断、能力差距、材料准备、岗位搜索、投递、面试、Offer选择和入职成长。岗位搜索、投递、面试和 Offer 相关能力属于后期阶段候选方向，不自动进入当前 MVP 主线；是否引入必须先满足《21天总准则》中的“当前 MVP 外部成熟方案吸收准则”。

### 数据护城河

数据库本身不是壁垒。壁垒是持续、低成本、合规地产生高质量数据并转化为决策：

- 求职行为数据库；
- 干预效果数据库；
- 真实结果数据库；
- 岗位与能力变化库；
- 评测与策略资产。

### 模型部署

规则和程序承担确定性任务；私有模型承担高频标准任务和敏感材料；云端高质量模型保留复杂判断和长尾上限；模型路由负责成本、风险和可用性。

### 商业化

B2C结果型阶段产品；标准化B2B学生分层和就业干预；成熟能力API。B2B和API必须建立在C端效果、数据和合规能力已证明之后。

## 6. 数据库原则

最重要的数据链：用户状态 → 系统判断 → 任务/干预 → 真实执行 → 质量与阻力 → 系统调整 → 求职结果。

数据必须有时间、来源、版本、原因、证据、统一失败原因码和结果观察窗口。只收集会影响产品判断的数据；敏感信息分级存储、授权、删除和脱敏。

## 7. 指标总框架

指标树：获客匹配 → 激活 → 执行 → 留存 → 状态迁移 → 外部结果 → 质量与信任 → 经济效率。

禁止以总注册、对话轮数、生成字数、计划次数、页面停留和无证据的完成率作为核心成功指标。

## 8. 模型与技术策略

业务代码围绕能力定义接口：diagnoseUserState、extractResume、extractJD、selectNextTask、generateDailyTask、evaluateExecution、adjustPlan、generateFeedback。

正式私有部署的前提：稳定用户和调用结构、标准任务集中、开源模型评测达标、总成本收益成立、存在隐私或稳定性硬要求，并具备云端兜底。

## 9. 商业边界

前期免费深测和低价一次性付费；中期21天核心产品加投递/面试阶段产品；后期B2C规模化、标准化B2B和API。

防止产品变成无限陪聊、重咨询或学校定制外包。人工介入必须记录原因、耗时和结果，并优先转化为产品能力。

## 10. 当前执行优先级

### P0

1. 统一四路线数据结构。
2. 任务包含目的、原因、标准、耗时、证据和失败处理。
3. 建立JourneyState、TaskExecution、Intervention、Outcome、ModelTrace。
4. 跑通完整事件链并支持单用户复盘。
5. 建立真实岗位验证和来源版本记录。

### P1

1. 招募陌生目标用户真实使用。
2. 每周复盘用户、任务、路线和模型错误。
3. 建立四路线人工评测集。
4. 定义关键行动、有效进展、真实完成和无效输出。
5. 出现有效案例后测试首次付费。

### P2

1. 根据失败模式优化动态计划。
2. 建立用户、任务、干预和结果标签。
3. 有数据后引入模型路由。
4. 建立以进展、执行、流失和结果为核心的看板。
5. 验证21天结束后的下一阶段产品。

**功能优先级 ≈ 对真实求职结果的影响 × 出现频率 × 数据闭环价值 ÷ 实现与维护复杂度。**

## 11. 阶段升级原则

没有证明有用，不进入规模化；没有证明可重复，不扩大人群；没有稳定调用和评测，不正式私有部署；没有标准化C端效果，不把B2B当作救命业务。

## 12. 总结

“21天”的长期方向不是做一个更会聊天的AI，也不是尽快拥有自己的本地大模型，而是成为真正理解普通本科应届生求职过程、能够选择下一步有效行动的决策系统。

最终护城河不是模型，也不是数据库容器本身，而是持续产生高质量真实数据的产品机制，以及基于这些数据形成的个性化求职决策与干预能力。
