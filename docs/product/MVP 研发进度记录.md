## 2026-08-05 JD 路线治理修订（P0 v1）

修订理由：最高治理原则中“至少给出 1-2 个最小修改”的旧表述，与诚实裁决所需的严格无需修改状态冲突。为避免系统在材料已经充分、准确时强行改写，本轮显式允许 0 个修改，同时保留一个可执行的确认、保存和记录行动。

本轮统一规则：

- 确需修改：给 1 个主行动和 1-2 个有真实来源的相关修改；用户确认后保存材料版本，并记录投递状态和观察点。
- 缺来源：不生成可直接粘贴的假设句；只给补事实行动，保存用户确认的补充来源后重新提交并重新判断。
- 严格无需修改：允许 0 个修改，但服务端必须检查前 3-5 条关键要求，确认每个保留判断都有来源、没有未支撑的关键要求、没有夸大或事实错误；用户确认并保存当前版本，再记录投递状态和观察点。
- 上述内部裁决名、关系标签和质量门术语不得展示给用户。

受影响文档（本隔离 worktree 内）：《21天总准则》《MVP AI工作流与安全边界设计》《MVP PM决策共识》《MVP UX信息架构第一版》《MVP UX准则》《MVP 测试用例与私测观察标准》《MVP 四路线输入输出数据设计》《MVP 页面低保真线框图》《MVP 页面线框与关键状态设计》《新MVP PRD》《MVP 研发进度记录》。

## 2026-08-05 JD 通用证据合同与失败恢复 P0 实施记录

- 新增请求级精确来源合同，服务端签发并复核来源 ID、内容哈希、版本、字段路径、逐字引用与 span；不持久化请求级 JD、材料、关系矩阵或 raw model output。
- JD 候选改为覆盖前 3–5 条要求的 typed mapping；服务端逐动作、工具、角色、数字、结果和强度词校验，并把项目推进/风险、数据/分析/复盘等原子拆开，不能再用粗概念桶错误 all-keep。
- 模型 reason 不对外展示；用户可见理由和补证据动作由服务端基于已签发引用派生。输入中的中英 prompt injection/bypass 变体只作为不可信数据处理。
- 三条闭环已分别实现：实际修改；补证据后返回输入并用用户确认的正向证据重新判断（明确未找到不并入材料）；严格 all-keep 确认当前版本并记录投递状态与观察点。
- 前端使用 requestId、draftRevision 与 idempotency，忽略迟到响应；AI 失败、保存失败、复盘失败分离，事务失败不覆盖旧行动、记录和轨迹。
- 语义/grounding/safety/product invalid 只做一次 primary 定向修复；机器不可用才做一次 primary 技术重试后尝试 Qwen；服务端 28 秒覆盖 request body read，caller abort 与 deadline 分开。
- 完成 40 条分层规则样例（8 条冻结隐藏）以及精确 AI 产品运营、关系拓扑、all-keep、冲突、注入、双语、长文本和失败预算回归。

提交前新鲜验证：最终聚焦后端 78/78、前端单元 39/39；全量 Vitest 942/942（另 1 skipped）；desktop/mobile 浏览器定向通过；lint、TypeScript、production build 与 `git diff --check` 通过；安全审计无 high/critical，仍有依赖链 4 个 moderate，强制自动修复会升级到声明范围外的 Next 版本，本轮不做越界升级。后端安全与前端治理最终只读复核均明确“可放行”，未发现剩余 P0/P1。
